# 變更日誌

本檔記錄重要的程式調整，方便團隊回溯。

---

## 2026-06-28　消除列表查詢的 N+1 問題（效能優化）

### 背景
多個「列出全部」的方法在 `for` 迴圈內逐筆呼叫 Repository，導致查詢數隨資料量線性成長（1 + N）。
資料量一大時 DB 連線與往返成本明顯上升。

### 共通做法
把「對照/關聯資料」在迴圈外**只查一次**載入記憶體，迴圈內改成記憶體比對／分組。
全部採用基礎 SE 語法（傳統 `for` 迴圈、`HashMap`、`ArrayList`），未使用 Stream / Lambda，方便維護。

### 調整內容

1. **`AdminMemberServiceImpl`（會員列表）**
   - `listAll()`、`list(tierNames, statuses)`：原本每位會員都呼叫
     `spendingTierRepository.findTierNameByAmount(amount)` 查級距。
   - 改為迴圈外 `spendingTierRepository.findAll()` 載入一次，新增私有方法
     `resolveTierName(tiers, amount)` 在記憶體比對金額級距。
   - 查詢數：`1 + N` → `2`。

2. **`AdminServiceImpl`（管理員列表）**
   - `listAll()`：原本每位管理員都呼叫 `findPermissionCodesByAdminId(adminId)` 查權限。
   - 新增 Repository 方法 `AdminRepository.findAllAdminPermissionCodes()`
     （一次撈出所有 `[admin_id, permission_code]`），在記憶體用 `HashMap<Integer, List<String>>` 依
     `admin_id` 分組。
   - 查詢數：`1 + N` → `2`。

3. **`AdminFarmerServiceImpl`（小農列表）**
   - `listAll()`：原本每位小農都呼叫
     `findTopByFarmer_FarmerIdOrderByReviewRoundDesc(farmerId)` 查最新審核。
   - 新增 Repository 方法 `FarmerReviewRepository.findAllReviewStatusRounds()`，
     **只查輕量欄位** `[farmer_id, review_status, review_round]`（刻意不碰 `LONGBLOB` 憑證檔，
     避免全量載入比 N+1 更糟），在記憶體挑出每位小農「最大輪次（最新）」那筆。
   - 新增批次版私有方法 `toAdminResponse(farmer, reviewStatus, reviewRound)`，維持管理員端
     顯示「真實審核狀態」（不套用小農端 `REVIEWING→PENDING` 遮蔽）的原行為。
   - DTO `FarmerProfileResponse` 補上 `setReviewRound(...)` setter 供批次組裝使用。
   - 查詢數：`1 + N` → `2`。

### 未調整（已評估）
- `getById()` / `getMyProfile()` 等單筆查詢本身只有 1 次關聯查詢，無 N+1，維持原樣。
- `AdminServiceImpl.assignPermissions()` 為寫入流程（逐筆 `INSERT`），權限代碼數量小且非讀取列表，
  本次不在「載入一次、記憶體比對」的範圍內，暫不調整。

### 備註
- 三個新增的 native query 皆回傳 `List<Object[]>`；`INT` 欄位於本專案 MySQL 設定下對應 Java `Integer`
  （與既有 `findPermissionIdByCode` 一致），`EnumType.STRING` 的 `review_status` 對應 `String`。
- 已通過 `mvnw.cmd compile` 驗證。

### 後續：合併 AdminFarmerServiceImpl 的兩個 toAdminResponse()
原本有兩個同名多載：單筆版 `toAdminResponse(farmer)`（自己查 DB）與批次版
`toAdminResponse(farmer, status, round)`（吃現成值），兩者「組裝 DTO」的邏輯重複。

改為**委派**：保留三參數版為「唯一組裝 DTO 的地方」，單筆版查完最新審核後把值取出再呼叫它。
- 組裝邏輯只剩一份，要改格式只改一處。
- 單筆仍查 1 次、列表仍無 N+1，效能不變；順帶修掉 `reviewStatus` 為 null 時對 null 呼叫 `.name()` 的潛在 NPE。

為什麼不用 varargs（`String...`）合併：varargs 只能表達「參數數量不同」，但這兩版真正的差異是
「**要不要自己查 DB**」，且帶的兩個值型別不同（`String` + `Integer`）。用 `String...` 會被迫把
輪次也轉成字串、並回到 `args[0]` 索引取值——等於把先前移除的 `Object[]` 寫法請回來，故不採用。
